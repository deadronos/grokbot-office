# ADR 0003: Server-Sent Events for the live stream

Status: Accepted

## Context

The viewer needs one-way, server-to-browser updates: bot status changes, task and
handoff events, and a hidden-bot refresh hint. Browsers connect rarely (a few open
office tabs), events are small JSON objects with a monotonically increasing sequence,
and the transport must survive a Mac that sleeps, a Tailscale proxy, and reconnects
without losing the gap. Clients also need to resume from the last event they saw.

The auth model is an `HttpOnly`, `Secure`, `SameSite=Strict` session cookie, because
`EventSource` cannot send an `Authorization` header.

## Decision

Use Server-Sent Events on `GET /api/stream` (`text/event-stream`), with
`GET /api/events?since=&limit=` as the replay endpoint.

- `EventSource` reconnects by itself. Each event frame carries `id: <seq>`, so the
  browser resends `Last-Event-ID` and the server resumes after it; `?since=` is the
  equivalent for clients that cannot set the header, and the header wins.
- A `retry: 3000` line and an initial `: open` comment make `onopen` fire and dev
  proxies flush immediately, even with nothing to replay.
- A `ping` frame every 25 s keeps proxies from idling the connection out and
  re-checks the credential each time, so a revoked token or session ends the stream.
- The hub is in-process (`apps/server/src/stream/hub.ts`), with a cap of 200
  concurrent streams (`503` beyond it) and a `closeAll()` used during shutdown.
- The sequence number is the stream id, so replay, live delivery and idempotent
  store application share one ordering key.

## Consequences

- One unidirectional protocol, no WebSocket dependency, no client-to-server messages.
  Anything the viewer writes uses a normal `POST` with the same cookie and a CSRF
  check.
- Reconnect semantics are the browser's, which is why gap-filling needs
  `Last-Event-ID`/`since` and the viewer probes `GET /api/state` on each stream error.
  An expired session surfaces as a stream error, not as a rejected handshake.
- Because streams are long-lived, shutdown must end them before closing listeners
  (otherwise `close` waits forever), and a session that stays open never goes idle:
  pings refresh `last_seen_at` by design.
- HTTP/1.1 limits a browser to roughly six connections per origin, which is why the
  viewer keeps exactly one stream per tab.
- WebSockets would add bidirectional messaging and per-connection auth, but the
  viewer never needs to push anything to the server that a `POST` cannot do.
